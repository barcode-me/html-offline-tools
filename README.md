_You can access all tools from Github Pages https://barcode-me.github.io/html-offline-tools. This is specially useful for the NFC card page that requires HTTPS._

A few helpful tools that you can run in a browser by opening a stand alone HTML file locally. It does not request any resources over the network and it is built with vanilla JS, HTML, CSS. Except for a QR code library that is embedded in the files. Some features such as Scanning QR codes only work in chromium browsers and in some OSs like macOS, but the tool can still be used without the scan QR feature.

- Generate Diceware passphrases [diceware-passphrase.html](./diceware-passphrase.html)
- Generate 12-word BIP39 seed phrases [bip39-seed-generator.html](./bip39-seed-generator.html)
- Convert text or binary files to Yeti phonetic rows [yeti-encoder-decoder.html](./yeti-encoder-decoder.html)
- Read and write NFC cards with optional password encryption [nfc-card-reader-writer.html](./nfc-card-reader-writer.html)
- Transfer files via QR codes [qr-file-transfer.html](./qr-file-transfer.html)
- Encrypt and decrypt text with one-time pads [one-time-pad-encryption.html](./one-time-pad-encryption.html)
- Encrypt and decrypt files or text with a password [secure-file-encryption.html](./secure-file-encryption.html)
- Open passwords and live TOTP codes from plain text or encrypted Base64 [password-manager.html](./password-manager.html)
- Encrypt 12-word BIP39 seed phrases into 132-bit shares [seed-one-time-pad-encryption.html](./seed-one-time-pad-encryption.html)

The QR transfer app is intended for small files. Even a single MB could take hours to transfer with this method. I recommend you transfer only content under a few KB. It is amazing for sending sensitive information between devices without the need for a USB drive, internet connection, LAN, Bluetooth. Perfect for airgap devices as long as you transfer small files.

The encryption and decryption pages with one-time pads are intended mainly as a tool to backup small sensible pieces of information. It is a very simple form of split secret. You can backup the one-time pad separate from the encrypted content. Only by having the two of the you can get access to the content. The main benefit is that they use a very simple algorithm and are considered to be unbreakable as long as the pad is not reused, it is not exposed, and it is cryptographically random.

It is for example a great way to backup passwords in two shares, as long as you use a secure device preferably airgapped, you can backup each share to a small veracrypt volume generated on the device. Transfer the volume file out via QR codes store it in multiple clouds and as long as you remember the password you have your own password backup. Not but seriously, don't use it as a password manager, this is more of a password backup.

The seed encryption page embeds the official 2,048 English BIP39 words and validates the SHA-256 checksum. Each share is exactly 33 hexadecimal digits (132 bits), with leading zeros preserved. QR codes and text downloads contain only that HEX value. To recover, XOR the two values, split the resulting 132 bits from the left into twelve 11-bit indices, and map them to the English BIP39 word list. This compact format is not compatible with the UTF-8 text decryption page. Any additional BIP39 passphrase must be backed up separately.

The Diceware page embeds all 7,776 entries from Arnold G. Reinhold’s original word list. Generate words with unbiased browser Crypto API dice rolls, or enter five physical dice rolls (digits 1–6) per word and append more as needed. Separators default to off. Apply random casing rerolls secure whole-word casing on each click; Restore default casing returns to the original words. Open the HTML file directly; no server, dependencies, or network access are needed. Passphrases are not persisted by the page.

The BIP39 generator offers automatic browser randomness, physical dice rolls, coin flips with custom side labels, and manual word entry with autocomplete (BIP39 lottery). Auto and lottery modes keep the first 128 bits of twelve word indices, preserving the last word’s first seven bits, and replace the remaining four bits with the SHA-256 checksum. Dice use the unbiased mapping `1→00, 2→01, 3→10, 4→11, 5→0, 6→1`; coin sides map to `0` and `1`. Physical entry stops at 128 bits and discards any extra final-roll bit. Fair, independent physical outcomes are required; human-selected words do not provide secure randomness. The page shows entry mappings, entropy, checksum, all twelve 11-bit word blocks, and an optional Standard SeedQR (48 numeric digits containing zero-based, four-digit word indices). The word list and QR encoder are embedded. Open the file locally in a modern browser; nothing is transmitted or persisted. Run regression checks with `node --test tests/*.test.cjs`.

The text/file-to-Yeti page (`yeti-encoder-decoder.html`) accepts UTF-8 text or the raw bytes of any uploaded file, without hex parsing, checksum prefixes, or a fixed input size limit. Whitespace in text and all file bytes are preserved. It preserves leading zero bytes in raw Base58, adds case-sensitive phonetic row checksums, and appends the five digit words derived from SHA-256, matching the supplied Python encoding algorithm. Results appear in a text area and can be downloaded. Large files require more time and browser memory and generate much larger output. This is not WIF or an original Yeti wallet recovery seed.

The password encryption page is based on [barcode-me/web-encryption secure.html](https://github.com/barcode-me/web-encryption/blob/main/secure.html). It keeps AES-256-GCM, PBKDF2-SHA-256 with 600,000 iterations, a random 16-byte salt, and a random 12-byte IV. Radio buttons select encryption/decryption and file/text input. Binary `.wec` downloads encrypt raw content bytes and the UTF-8 filename, with an authenticated header containing byte offsets. Overhead is 62 bytes plus the filename length. The complete byte layout is documented inside the page. Optional Base64 text enables copy/paste decryption without changing binary downloads. Original JSON containers and version 1 / 100,000-iteration encryption are not supported. Decrypted files retain their names and exact bytes; MIME types are not stored. The page works offline with browser Web Crypto and processes files in memory. Run its regression checks with `node --test tests/secure-file-encryption.test.cjs`.

Yeti encoding optionally encrypts text or file bytes with the same binary format as `secure-file-encryption.html` before converting to phonetic rows. Enable password decryption when decoding to restore the original bytes and filename. You can also encode an existing `.wec` file without additional encryption, then decrypt its Yeti record with the same password. With decryption off, decoded encrypted bytes download as `recovered.wec` for use in the standalone encryption page. Legacy 100,000-iteration encryption and JSON containers are not supported.

## Running secure-file-encryption

Run `npm link` on this project directory and the node.js script will be available anywhere in your system.

The NFC card page uses Web NFC for NDEF-compatible tags. Open it over HTTPS in Chrome on an NFC-enabled Android phone; ordinary local-file use and desktop/iPhone browsers are not supported. The page has no external dependencies or network requests. Text is written as an NDEF text record; hexadecimal pairs are parsed into raw bytes in a binary MIME record. Writing replaces the existing NDEF message. Reads show each text record as text and binary records as hex, preserving leading zeros. Optional password encryption uses the exact WENC v2 format from the file-encryption page; encrypted text uses the authenticated filename `text.txt`, and encrypted hex uses `data.bin`. Decryption displays `.txt` payloads as strict UTF-8 when valid and other payloads as hex. Encryption adds 70 bytes for these filenames, in addition to NDEF overhead; capacity and write protection are enforced by the NFC device. Hardware behavior requires testing on an actual phone/tag. Run automated conversion, encryption compatibility, and mocked NFC workflow checks with `node --test tests/nfc-card-reader-writer.test.cjs`.

The QR transfer page accepts files, UTF-8 text, or hexadecimal byte pairs. Received content defaults to strict UTF-8 when valid and otherwise displays hex; the display controls allow switching valid text to hex, and Copy copies the selected representation. Downloads retain the original bytes. Static hex transfers use a Base64 JSON envelope (`binary_static`) to preserve binary bytes through text-only QR decoders and require this page to recover the bytes. Chunked transfers keep the existing protocol. The receiver still requires native QR support from `BarcodeDetector`. Run the binary-input and display regression checks with `node --test tests/qr-file-transfer.test.cjs`.

QR receive mode accepts an optional decryption password before scanning. Encrypted transfers complete without one and display the ciphertext, with a JSON download retaining the ciphertext, salt, IVs, and encrypted metadata. Providing a password decrypts after receipt; incorrect passwords leave the encrypted transfer available for download and retry without rescanning. This uses the QR page’s existing encrypted-transfer format.

Plain-text NFC records (including decrypted text) now use the password manager’s line-based entry display: `Label:password` values start masked with individual Reveal and Copy controls, and `otpauth://totp/` lines produce live TOTP codes. The full decoded text also starts masked. Binary records remain hex and are never scanned for entries. Clearing results stops the code refresh timers.
