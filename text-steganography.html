Text steganography

Hide ASCII text or raw bytes inside a random hex sequence, then disguise that sequence as the "signature" of a plain-text purchase order. A passphrase deterministically scatters which hex characters carry data. Everything runs locally in your browser; nothing is uploaded or saved by the page.

The payload itself is not encrypted: anyone with the passphrase can read it. To protect the content as well, encrypt it first with Secure file encryption and hide the result as hex bytes. Any edit to the characters of the signature itself (not just surrounding wording) destroys the hidden data, so copy it exactly. The downloaded file is a plain, uncompressed PDF generated entirely in the page with the standard Helvetica fonts and no metadata.

Embedding algorithm and format

The target text is a sequence of L lowercase hex characters, L being 128, 256, 512 or 1024 (512, 1024, 2048 or 4096 bits). Each character is one nibble (4 bits) and can be replaced independently, unlike image LSB steganography which only flips a bit's least significant bit.

  1. A random 16-byte salt (128 bits) is written as 32 literal hex characters at the start of the sequence. These 32 characters are excluded from everything that follows.

  2. The UTF-8 passphrase and salt go through PBKDF2-SHA-256 with 600,000 iterations; crypto.subtle.deriveBits returns 256 bits that become an AES-256-CTR key. The RNG is the AES-CTR keystream of zero bytes with an all-zero initial 128-bit counter block (64-bit big-endian counter), consumed most significant bit first.

  3. The remaining M = L − 32 characters form the pool. A partial Fisher–Yates shuffle picks characters one at a time: for step i, j = i + uniform(M − i), swap pool positions i and j, and use the character now at position i. uniform(n) reads only ceil(log2(n)) bits and rejects values ≥ n to stay unbiased.

  4. The record below is written nibble by nibble (high nibble of each byte first) into the chosen characters. Extraction repeats the same steps, reading the header first to learn how many more characters to visit.

Byte offset Bytes Field
0 4 Magic: ASCII STXT
4 1 Version: 1
5 1 Payload type: 0 = ASCII text, 1 = binary (from hex)
6 4 Payload length in bytes, unsigned big-endian
10 4 First 4 bytes of SHA-256(payload)
14 Length Payload bytes. Hex input is stored as the raw bytes it represents, not as hex characters.

Capacity in bytes is floor(M / 2) − 14: 34 bytes at 512 bits, 98 bytes at 1024 bits, 226 bytes at 2048 bits, 482 bytes at 4096 bits. The checksum detects a wrong passphrase or a modified sequence; it is not a cryptographic authenticator.

The full L-character sequence (salt plus scattered payload) is packed as L / 2 raw bytes and Base58-encoded (same alphabet as Bitcoin, leading zero bytes preserved as leading "1" characters). That string is placed on its own line in a generated purchase order document as a "Signature" value, and the document is offered both as plain text (shown in the page) and as a downloadable PDF built in the page with a minimal, uncompressed PDF 1.4 writer (standard, non-embedded Helvetica fonts, Letter pages, no metadata). The PDF word-wraps ordinary text and hard character-wraps the signature itself, since it has no spaces to wrap at; this only affects how it prints, not the underlying characters. Extraction scans the pasted text for the longest run of 20 or more consecutive Base58 characters, Base58-decodes it, checks that the decoded byte length matches one of the four supported sizes, and runs the same scatter algorithm to read the header and payload. Surrounding wording can be freely edited or replaced as long as the signature characters themselves stay intact and on one unbroken run, which is why extraction should use the plain text (or the signature-only field) rather than text copied back out of the PDF.
